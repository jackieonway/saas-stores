# 门店成员归属契约

平台维护身份与组织成员，门店服务维护负责人、员工关联和日报。业务数据库不连接平台用户表。负责人和员工显示名来自平台受控成员接口，浏览器不能提交显示名或伪造归属。

## 允许的目录用途

| 资源 / 动作 | 用途 |
| --- | --- |
| `store/create` | 创建门店时选择负责人 |
| `store/update` | 修改门店时选择或校验负责人 |
| `store-staff/assign` | 将有效成员关联到门店 |

平台数据策略必须在当前应用的 `memberLookups` 中登记相同用途，调用用户还需对应的功能 permission 和数据授权。`read`、`unassign` 及日报动作都不能用于查用户目录。示例位于 `../policy.example.json`。

浏览器调用 `GET /stores-api/members?resource=store&action=create`，可带允许的 `organizationId`、`page`、`size` 和 `q`。业务后端使用当前应用 Bearer 调用平台 `/api/apps/stores/members`；实际写入通过 `/api/apps/stores/members/{user}` 再次检查。

目录只返回允许租户、组织中的当前有效直接成员。默认目标为当前组织，显式目标也必须通过数据范围和组织硬上限。响应只保留用户 ID、显示名及组织 ID，分页、组织和重复成员均由服务再次验证。目录候选不是永久的成员资格证明。

## 归属与 SELF

门店 owner 是创建人，员工关联 owner 是员工本人，日报 owner 是录入人。负责人不自动获得门店 owner 身份；关联的创建人不自动获得员工行的 SELF 权限。每种资源都使用自己的数据授权，并与租户、组织硬边界相交。

已有门店的负责人修改与员工关联先在当前范围内读取目标，记录组织、owner、旧值和版本。成员 HTTP 调用期间不占用业务连接或行锁。随后短事务锁定业务目标，再核对前置读取值和版本，不能借负责人变化扩大 owner 范围。

## 绝对时效窗口

单成员验证的有效窗口从 HTTP 发起前开始，长度是 `min(PLATFORM_AUTH_TIMEOUT_MS, 3000ms)`。响应传输、后续连接池等待和行锁等待都消耗同一窗口。成员校验绑定操作人、租户、当前组织、资源动作、目标组织和目标用户，事务中不得续期或复用到其他操作。

授权或成员窗口在提交前失效时，写入拒绝并回滚；成员超时可返回 `503 MEMBER_VALIDATION_EXPIRED`。若 COMMIT 已发生但无法确认结果，则返回创建或写入结果未知，客户端需查原始目标及版本，不得自动重发。具体响应和恢复流程见 [API 契约](../API.md)。

平台成员撤销与门店数据库提交之间没有分布式事务。最后一次平台检查到 COMMIT 仍有短暂竞态，当前实现限制窗口但不承诺跨库强一致。需要更强保障时，必须增加平台侧可验证的提交协调协议。

## 前端更新与验收

qiankun `update` 传递新的 `props.platform`。身份、组织或授权替换会取消旧请求并隔离旧数据，旧候选和旧表单不能继续提交。相同身份的合法续期也须重新读取编辑版本，再由用户明确采用。

验收至少包含：三个允许用途、无权限用途拒绝、目标组织越界、成员撤销、成员窗口耗尽、锁后目标版本变化，以及提交后结果未知的显式核对。管理员单次成功不能覆盖普通用户和跨组织场景。
